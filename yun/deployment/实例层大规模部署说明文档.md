# 实例层大规模部署说明文档

## 1. 适用范围

本文档描述的是**生产阶段的实例层 EC2** 怎么部署。

目标形态：

- 1 台实例层 EC2
- 1 个 Agent 进程
- 20 个 Android Worker（你目前计划把它们做成 20 个 Waydroid 槽位）
- 每个 Worker 内运行 1 个 APK
- 每个 Worker 都能被当前 Agent 代码当成一个独立实例管理

本文档与 `NewUI/yun/deployment/调度层大规模部署说明文档.md` 强耦合。

---

## 2. 先说最重要的现实约束

### 2.1 当前代码层面的“实例”定义

对当前 Agent 来说，一个实例槽位不是一句“开了一个 Waydroid”就算完成，而是必须满足：

- 有全局唯一 `instance.id`
- 有唯一 `adbTarget`
- 有唯一 `probePort`
- 有唯一 `wsPort`
- 宿主机能通过 `adb connect <adbTarget>` 连进去
- 宿主机能做 `adb forward tcp:<probePort> tcp:8080`
- 手机 B 能访问 `ws://<PUBLIC_WS_HOST>:<wsPort>/ws`

### 2.2 当前代码下，同机 20 个实例的区分方式是什么

**答案是：外部靠 `wsPort`，内部靠 `instance.id + adbTarget + probePort + wsPort`。**

具体行为如下：

1. 每个 Android Worker 内部 APK 都监听 Android 内部 `8080`
2. Agent 通过各自独立的 `adbTarget` 连接不同 Worker
3. Agent 对每个 Worker 执行：
   - `adb connect <adbTarget>`
   - `adb forward tcp:<probePort> tcp:8080`
4. Nginx 再把公网 `wsPort` 反代到本机 `probePort`
5. 调度层收到 `wsPort` 后，给手机拼出：
   - `ws://<PUBLIC_WS_HOST>:<wsPort>/ws`

所以最终链路是：

```text
手机 B -> wsPort -> Nginx -> probePort -> adb forward -> Worker 内 APK:8080
```

### 2.3 关于“20 个 Waydroid / EC2”的一句实话

当前仓库没有提供“Waydroid 多实例编排器”。

因此你要把这 20 个槽位跑起来，必须额外实现或选型一层**Android Worker 编排层**，让每个 Worker 都满足上面的四元组契约。

也就是说：

- 当前 Agent / Scheduler 代码已经支持“一台 EC2 管多个实例”
- 但“20 个独立 Waydroid Worker 如何在一台 Linux 宿主上编排出来”，不是当前仓库已经完成的部分
- Waydroid 官方文档也没有给出这个场景的开箱即用部署流程

生产建议：

- 把“每个 Worker 是什么”单独抽象成运行时槽位
- 只要最终给 Agent 暴露出唯一 `adbTarget/probePort/wsPort` 即可

## 3. 推荐的实例层服务器规划

## 3.1 EC2 基线建议

你给出的目标机型是 `r7g.xlarge`，这个方向可以作为**试点**，但请把下面这句话当成正式要求：

> **“单 EC2 20 个 Android Worker”是容量目标，不是当前代码自动保证值。**

必须先做压测，重点关注：

- 每个 Worker 冷启动耗时
- `pm clear + am start + getBrands` 的平均时延
- 20 个实例同时 `reserved -> applyCar` 时的 CPU 峰值
- 宿主机内存占用
- 网络带宽和 WebSocket 并发数

### 3.2 生产推荐网络关系

- 调度层 EC2 与实例层 EC2 最好放在**同一 VPC 内可互通**
- 调度层访问实例层 Agent 时，优先走**实例层私网 IP**
- 手机 B 访问实例 WebSocket 时，走**实例层公网 IP / 域名**

这和当前代码正好匹配：

- `serverIp`：控制面地址，给调度层用
- `publicWsHost`：数据面地址，给手机 B 用

## 7. 每个 Android Worker 需要满足的行为契约

无论你最终把 Worker 实现成什么，下面这些行为都必须成立：

### 7.1 启动前提

- Worker 能被宿主机 ADB 连接
- APK 已安装
- APK 包名和 Activity 与 Agent 配置一致

### 7.2 冷启动契约

Agent 当前会对每个 Worker 执行下面一整套流程：

1. `adb connect <adbTarget>`
2. `adb forward tcp:<probePort> tcp:8080`
3. `adb shell pm clear <package>`
4. `adb shell am start -n <package>/<activity>`
5. 轮询 `getBrands`
6. 应用默认车型

所以你们的 Worker 编排层必须允许：

- 频繁 `pm clear`
- 频繁 `am start`
- `adb forward` 重复覆盖

### 7.3 运行中契约

- APK 内 WebSocket 服务在 Worker 内始终监听 `8080`
- 宿主机把 Worker 暴露为唯一 `adbTarget`
- 宿主机 Nginx 把唯一 `wsPort` 路由到对应 Worker 的 `probePort`

## 8. Agent 部署步骤

## 8.1 拉代码并构建

```bash
sudo mkdir -p /opt/obd
sudo chown -R "$USER":"$USER" /opt/obd
cd /opt/obd

git clone <你的仓库地址> repo
cd repo/NewUI/yun/agent

npm ci
npm run build
```

## 8.2 生成 `INSTANCES_CONFIG`

推荐不要手写 20 条，直接生成。

```bash
SERVER_ID=ec2-apne1-a01

node -e '
const sid = process.env.SERVER_ID;
const arr = Array.from({ length: 20 }, (_, idx) => {
  const i = idx + 1;
  return {
    id: `${sid}_inst_${String(i).padStart(2, "0")}`,
    wsPort: 8080 + i,
    probePort: 18080 + i,
    adbTarget: `127.0.0.1:${5554 + i}`,
    packageName: "com.companyname.cardemo",
    activityName: "crc64b16463db6be126c1.MainActivity"
  };
});
console.log(JSON.stringify(arr));
' > /etc/obd-agent/instances.generated.json
```

## 8.3 写 Agent 环境文件

`/etc/obd-agent/agent.env`

```bash
SERVER_ID=ec2-apne1-a01
AGENT_PORT=4000
SCHEDULER_URL=http://<调度层地址>:8080/api
PUBLIC_WS_HOST=<这台实例EC2的公网IP或域名>
PUBLIC_WS_SCHEME=ws
INSTANCES_CONFIG=<把 /etc/obd-agent/instances.generated.json 压成一行后填进来>
```

### 8.4 关于 `SCHEDULER_URL`

这里必须和调度层文档一致，推荐直接写：

`http://<调度层静态IP或域名>:8080/api`

原因：

- 当前手机 B 端也是这个入口形状
- 当前调度层文档也会按这个入口暴露
- 这样实例层和调度层不会出现“一个写根路径、一个写 `/api`”的兼容问题

### 8.5 关于 `PUBLIC_WS_HOST`

这里填的是**手机 B 真正可访问**的地址。

推荐值优先级：

1. 实例 EC2 专属域名
2. 实例 EC2 公网 IP / EIP
3. 留空，交给 Agent 自动探测

如果你希望实例公网 IP 变化后尽快生效，推荐：

- 由实例启动脚本显式写入 `PUBLIC_WS_HOST`
- 或在实例重启后立即重启 Agent，使它立刻上报最新地址

## 9. Agent systemd 服务

`/etc/systemd/system/obd-agent.service`

```ini
[Unit]
Description=OBD Instance Agent
After=network.target nginx.service
Wants=network.target

[Service]
Type=simple
WorkingDirectory=/opt/obd/repo/NewUI/yun/agent
EnvironmentFile=/etc/obd-agent/agent.env
ExecStart=/usr/bin/node /opt/obd/repo/NewUI/yun/agent/dist/index.js
Restart=always
RestartSec=5
StandardOutput=append:/var/log/obd-agent/agent.log
StandardError=append:/var/log/obd-agent/agent.err.log

[Install]
WantedBy=multi-user.target
```

启用：

```bash
sudo mkdir -p /var/log/obd-agent
sudo systemctl daemon-reload
sudo systemctl enable --now obd-agent
sudo systemctl status obd-agent
```

## 10. 实例层 Nginx 配置

## 10.1 为什么实例层一定要有 Nginx

因为当前代码要求：

- `wsPort` 是给手机 B 的公开地址
- 但 APK 真实监听的是 Worker 内部 `8080`
- Agent 探针走的是本机 `probePort`

因此最稳妥的生产结构是：

`wsPort -> Nginx -> probePort -> adb forward -> Worker:8080`

## 10.2 生成 20 个监听端口

```bash
for i in $(seq 1 20); do
  ws=$((8080 + i))
  probe=$((18080 + i))
  sudo tee /etc/nginx/conf.d/obd-worker-${i}.conf >/dev/null <<EOF
server {
    listen ${ws};
    server_name _;

    location /ws {
        proxy_pass http://127.0.0.1:${probe};
        proxy_http_version 1.1;
        proxy_set_header Upgrade \$http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host \$host;
        proxy_set_header X-Real-IP \$remote_addr;
        proxy_set_header X-Forwarded-For \$proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto \$scheme;
        proxy_connect_timeout 60s;
        proxy_send_timeout 60s;
        proxy_read_timeout 3600s;
        proxy_buffering off;
    }

    location /health {
        return 200 "OK\\n";
        add_header Content-Type text/plain;
    }
}
EOF
done

sudo nginx -t
sudo systemctl reload nginx
```

## 11. 安全组与网络要求

## 11.1 实例层 EC2 入站

必须放行：

- `22/tcp`：仅运维出口 IP
- `4000/tcp`：仅调度层安全组
- `8081-8100/tcp`：给手机 B 访问实例 WebSocket

不要放行：

- `5555-5574/tcp`
- `18081-18100/tcp`

这两组只允许宿主机本地使用。

## 11.2 实例层 EC2 出站

必须允许：

- 访问调度层 `8080/tcp`
- 访问系统更新源

## 13. 生产运行时建议

### 13.1 先用 2 槽位验证全链路，再开 20

推荐顺序：

1. 先部署 `01`、`02` 两个槽位
2. 跑通注册、分配、连接、释放
3. 再扩到 `20`

### 13.2 每个 Worker 的日志要独立

最少要能回答：

- 哪个槽位冷启动失败
- 哪个槽位 `getBrands` 卡住
- 哪个槽位 `applyProfile` 失败

### 13.3 当前代码还有一个运维注意点

当前调度层会记录 `lastHealthAt`，但没有真正按“Agent 长时间不上报”自动剔除实例。

所以实例层生产建议必须配：

- `systemd Restart=always`
- 机器级监控
- Agent 日志告警

## 14. 实例层与调度层的耦合清单

上线前逐项核对：

- `SCHEDULER_URL` 是否写成 `http://<调度层地址>:8080/api`
- 调度层是否真的把 `/api/agent/health` 转发到调度服务根路由 `/agent/health`
- `PUBLIC_WS_HOST` 是否是手机可达地址
- `serverIp` 是否是调度层可达地址
- `agentPort=4000` 是否已对调度层放通
- `wsPort=8081~8100` 是否已对手机放通
- `instance.id` 是否全局唯一
