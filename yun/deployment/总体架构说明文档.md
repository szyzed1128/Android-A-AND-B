# 总体架构说明文档

## 1. 文档定位

这份文档是 `NewUI/yun` 当前代码形态下的**生产部署总说明**，用于把下面两份落地文档串起来：

- `NewUI/yun/deployment/实例层大规模部署说明文档.md`
- `NewUI/yun/deployment/调度层大规模部署说明文档.md`
- `NewUI/yun/deployment/Waydroid多实例隔离与并发稳定化避坑文档.md`

阅读顺序建议：

1. 先看本文件，确认架构边界、端口契约、你当前理解里哪些是对的、哪些需要修正。
2. 再看 `Waydroid多实例隔离与并发稳定化避坑文档`，先理解这次真实排障里哪些坑是“单实例默认假设”导致的。
3. 再看调度层文档，先把独立调度层 EC2 部署起来。
4. 最后看实例层文档，按一台实例 EC2 上 20 个实例槽位的方式部署。

## 2. 先给结论：你当前理解里哪些是对的

### 2.1 这些理解是对的

1. **生产阶段调度层和实例层应该分开部署。**
   - 当前同机只是开发/验证阶段节省成本。
   - 生产应该拆成：
     - 1 台调度层 EC2
     - N 台实例层 EC2

2. **实例层应该主动向调度层注册。**
   - 当前代码就是 `Agent -> Scheduler` 主动健康上报式注册。
   - 不是调度层主动发现实例。

3. **实例层 IP 可以变化，调度层地址最好保持稳定。**
   - 手机 B 端先连调度层，再从调度层拿实例 `wsUrl`。
   - 对“新分配”的会话来说，实例层 IP 变化后，只要 Agent 重新上报，调度层就能学到新地址。

4. **实例在当前实现里确实主要靠端口区分。**
   - 这一点不是“设想”，而是当前代码契约直接决定的。

## 3. 你当前理解里需要修正的点

### 3.1 不能把“多实例区分”理解成只有端口

当前代码里，同一台实例 EC2 上的一个实例槽位，至少由下面四元组来唯一标识：

- `instance.id`
- `adbTarget`
- `probePort`
- `wsPort`

其中：

- `instance.id`：调度层全局唯一 ID
- `adbTarget`：Agent 控制这一台 Android Worker 的 ADB 入口
- `probePort`：Agent 本机探针端口
- `wsPort`：对 B 端暴露的公网/反代端口

所以，**外部看起来是靠端口区分，内部真正运行时是“实例 ID + ADB 目标 + 本地探针端口 + 对外端口”一起区分。**

### 3.2 当前代码不是“路径分流”，而是“端口分流”

这一点非常关键。

当前调度层给手机 B 返回的实例地址，固定是：

`ws(s)://<publicWsHost>:<wsPort>/ws`

也就是说：

- `host` 是按 **整台实例服务器** 上报的
- `/ws` 路径是固定的
- **每个实例唯一变化的是 `wsPort`**

因此当前代码下：

- 同一台 EC2 上 20 个实例槽位，必须用 **20 个不同端口**
- 不能靠 `/ws/1`、`/ws/2` 这种路径区分
- 也不能在“同一 EC2 的 20 个实例”里给每个实例返回不同 host，因为当前 `publicWsHost` 是按 Agent/服务器级别上报，不是按实例级别上报

### 3.3 “只要调度层 IP 静态就完全不会有 IP 变化问题”这句话要加条件

更准确的说法是：

- **对新分配的会话**：只要调度层地址稳定，实例层 IP 变化不是根本问题，因为 Agent 会重新上报实例地址。
- **对已经在运行中的会话**：如果实例层公网 IP 在会话中途变化，已经下发给手机的旧 `wsUrl` 不会自动改写，当前连接还是会中断。

所以这句话应改成：

> 调度层地址稳定后，实例层地址变化不会影响后续新分配，但会影响已经在运行中的旧连接。

### 3.4 实例层不是“只要能访问调度层”就够了

当前架构有两条链路：

- **注册链路**：`Instance Agent -> Scheduler`
- **控制链路**：`Scheduler -> Instance Agent`

因此实例层除了要能主动访问调度层，还必须满足：

- 调度层能回连到实例层 Agent 的 `agentPort`

否则会出现：

- 调度层能看到实例已注册
- 但在真正分配时，无法调用 `/instance/:id/applyCar`
- 结果是“看得见、用不了”

### 3.5 “20 个 Waydroid 实例 / EC2”这件事，当前最大的不确定点不在调度代码，而在 Android 运行时编排

这是你这段话里最需要单独指出的一点。

当前代码只要求每个实例槽位满足这些运行契约：

- 有独立的 Android 运行环境
- 有独立的 ADB 入口
- APK 内部 WebSocket 服务始终监听 Android 内部 `8080`
- 宿主机能把每个槽位映射成独立 `probePort`
- 宿主机能把每个槽位映射成独立 `wsPort`

但是：

- **当前仓库虽然已经补出了脚本化部署入口**：
  - `NewUI/yun/deployment/scripts/bootstrap_scheduler_host.sh`
  - `NewUI/yun/deployment/scripts/bootstrap_host.sh`
  - `NewUI/yun/deployment/scripts/bootstrap_slot1.sh`
  - `NewUI/yun/deployment/scripts/create_instance.sh`
- **但这不等于“任意 Linux 宿主机开箱即用”**
- **它仍然依赖 ARM64 Ubuntu + Waydroid + binder/binderfs 内核能力这一整套前提**
- **Waydroid 官方文档也没有给出“同机 20 个独立实例”的官方开箱即用方案**

因此本套文档里会使用一个更精确的术语：

> **Android Worker（实例槽位）**

你可以把它实现成：

- 1 个隔离好的 Waydroid Worker
- 或 1 个轻量 Android Guest
- 或 1 个你们自行封装出来的多实例 Android 运行单元

只要它满足当前 Agent 代码的四元组契约即可。

补充一句最容易误解的边界：

- 如果走**完整新机部署链路**：
  - 调度层 EC2：`bootstrap_scheduler_host.sh`
  - 实例层 EC2：`bootstrap_host.sh -> bootstrap_slot1.sh -> create_instance.sh`
  - **不需要**你手工先有一个 Waydroid 实例
- 如果只走**扩容链路**：
  - 直接执行 `create_instance.sh`
  - **必须先有**官方 `slot_1` 基线，以及 `/var/lib/waydroid/images`

## 4. 当前代码的生产契约

### 4.1 手机 B 端如何找到调度层

当前客户端代码会把用户输入的 `cloudHost` 固定推导成：

`http://<cloudHost>:8080/api`

因此当前生产部署下，**调度层对手机 B 的入口必须兼容这个形状**：

- 协议：`http`
- 端口：`8080`
- 前缀：`/api`

如果你未来要改成：

- `https://scheduler.example.com`
- 或 `443`
- 或不带 `/api`

则需要同时改客户端 `deriveSchedulerUrl()` 的实现。

### 4.2 Agent 如何注册到调度层

实例层 Agent 启动后会：

1. 初始化自己管理的全部实例槽位
2. 立即执行一次健康上报
3. 后续每 60 秒继续上报一次

上报给调度层的信息包含：

- `serverId`
- `serverIp`
- `publicWsHost`
- `publicWsScheme`
- `agentPort`
- `instances[]`

其中 `instances[]` 内每项至少包含：

- `id`
- `wsPort`
- `agentStatus`
- `health`

### 4.3 调度层如何反向控制实例层

调度层收到 Agent 上报后，会把实例登记进 Redis。

当手机 B 请求“申请实例”时，调度层会：

1. 从空闲池取一个实例
2. 根据实例记录中的 `serverIp + agentPort`
3. 调 Agent 的：
   - `/instance/:id/applyCar`
   - `/instance/:id/reset`

因此：

- `publicWsHost` 是给手机 B 用的数据面地址
- `serverIp` 是给调度层回调 Agent 用的控制面地址

这两个地址可以相同，也可以不同。

生产推荐做法：

- `serverIp`：实例 EC2 在 VPC 内可达的私网 IP
- `publicWsHost`：实例 EC2 的公网 IP、EIP 或域名

当前 Agent 控制面地址的优先级是：

1. `SERVER_IP_OVERRIDE`
2. 云元数据里的私网 IP（例如 AWS `local-ipv4` / 阿里云 `inner-ipv4`）
3. `hostname -I` 的第一项

### 4.4 调度层如何把实例地址回给手机 B

调度层最终返回给手机的 `wsUrl` 形状固定是：

`<scheme>://<publicWsHost>:<wsPort>/ws`

这里再次说明：

- **当前实现里，同一台实例 EC2 上的多实例区分方式就是 `wsPort`**
- 所以同机 20 个实例，必须规划 20 个对外端口

## 5. 生产拓扑推荐

### 5.1 推荐拓扑

```text
手机 B
  |
  | 1) http://<scheduler-host>:8080/api
  v
调度层 EC2
  - Nginx(8080)
  - Scheduler Node(3000)
  - Redis
  |
  | 2) HTTP 回调控制
  v
实例层 EC2 (多台)
  - Nginx(8081~8100)
  - Agent Node(4000)
  - Android Worker 01..20
      - 每个 Worker 内 APK 监听 8080
      - 每个 Worker 对宿主映射独立 adbTarget / probePort / wsPort
```

补充两条当前正式约束：

- `adbTarget/probePort/wsPort` 只是同一实例身份证的不同投影，不能把“多实例”理解成“只多开端口”
- 车型目录接口（`/api/catalog/brands`、`/api/catalog/profiles`）现在由调度层优先读 Redis 缓存；缓存过期时再向空闲实例实时刷新，刷新失败时回退旧缓存

### 5.2 每台实例 EC2 的 20 个槽位建议

- `agentPort`：`4000`
- `wsPort`：`8081 ~ 8100`
- `probePort`：`18081 ~ 18100`
- `adbTarget`：`127.0.0.1:5555 ~ 127.0.0.1:5574`

也就是：

- 对手机 B：通过 `8081 ~ 8100` 区分 20 个实例
- 对 Agent：通过 `5555 ~ 5574` 和 `18081 ~ 18100` 区分 20 个实例

## 6. 这三份文档之间的耦合点

这部分是为了避免“各写各的，最后不兼容”。

### 6.1 调度层文档必须和实例层文档一致的地方

1. **实例主动注册**
   - 调度层必须暴露 `/api/agent/health`
   - 实例层 Agent 必须把 `SCHEDULER_URL` 指到兼容 `/api` 的入口

2. **控制回调**
   - 调度层必须能访问实例层 `serverIp:agentPort`
   - 实例层安全组必须允许调度层访问 `agentPort`
   - 如果实例有多网卡或 `hostname -I` 第一项不是正确控制面地址，应显式设置 `SERVER_IP_OVERRIDE`

3. **车型目录语义**
   - 调度层给 B 端返回的 `profileIndex`，必须是 `getProfiles(brand)` 返回数组内的下标
   - `applyProfile` / `applyCar` 的语义是 `brand + profileIndex`，不是全局 profileId
   - 目录接口允许使用缓存降级，但真正分配实例时仍必须把 `brand + profileIndex` 下发到具体实例执行
   - 目录缓存成立的前提是：同一实例层机器上的各槽位运行相同 APK 构建与相同车型目录数据；升级 APK 时应整体滚动并刷新缓存

4. **实例地址生成**
   - 实例层必须保证 `publicWsHost + wsPort + /ws` 真实可达
   - 调度层只是拼 URL，不会替你兜底改路由

5. **端口规划**
   - 实例层 `wsPort` 和调度层 Redis 登记必须一致
   - 调度层不会做二次端口转换

6. **当前客户端入口假设**
   - 手机 B 仍然固定从 `http://<scheduler-host>:8080/api` 入场
   - 生产环境不要把调度 API 改成别的外部形状，除非同步改客户端
