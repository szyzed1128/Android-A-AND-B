# 调度层大规模部署说明文档

## 1. 适用范围

本文档描述的是**独立调度层 EC2** 的创建、部署、反向代理和与实例层的耦合方式。

目标形态：

- 1 台独立调度层 EC2
- 对外提供：
  - `http://<scheduler-host>:8080/api`
  - `http://<scheduler-host>:8080/dashboard`
- 对内运行：
  - Scheduler Node 服务
  - Redis
  - Nginx

这份文档默认你当前**不改手机客户端代码**。

---

## 2. 为什么调度层必须这样暴露

当前手机客户端会把用户输入的 `cloudHost` 固定推导成：

`http://<cloudHost>:8080/api`

所以为了和当前代码直接兼容，调度层对外入口必须满足：

- 协议：`http`
- 端口：`8080`
- API 前缀：`/api`

如果你未来想改成：

- `https://scheduler.example.com`
- `443`
- 不带 `/api`

请把它作为**后续代码改造项**，不要在当前生产文档里偷换入口形状。

---

## 3. 调度层服务器建议

## 3.1 服务器角色

调度层这台机器负责：

- 给手机 B 提供统一入口
- 管理 session
- 管理 Redis 中的实例注册表和空闲池
- 接收 Agent 注册
- 回调 Agent `applyCar / reset`

### 3.2 推荐资源基线

调度层比实例层轻很多。

当前代码形态下，它主要是：

- Express HTTP
- Redis
- Nginx 反代

因此可以先从“轻量但稳定”的 EC2 起步。

建议原则：

- 至少 2 vCPU
- 至少 4GB 内存
- 系统盘足够存日志和构建产物

### 3.3 调度层地址建议

推荐至少满足一个条件：

1. 绑定 **Elastic IP**
2. 或绑定一个固定域名，并长期指向这台机器

当前最省心方案：

- 调度层 EC2 绑定 **Elastic IP**
- 手机 B 在 `cloudHost` 输入这个静态 IP

## 4. 需要安装的软件和包

当前正式文档与脚本的验收基线是 **Ubuntu 22.04 LTS**。

- 如果你走当前正式脚本链路：
  - 调度层 EC2 用 `bootstrap_scheduler_host.sh`
  - 实例层 EC2 用 `bootstrap_host.sh / bootstrap_slot1.sh`
  - 实例层仍需 `Ubuntu 22.04 LTS + ARM64`
- `Ubuntu 24.04` 并不是当前已经验收的部署基线。

```bash
sudo apt update
sudo apt install -y \
  curl \
  ca-certificates \
  git \
  nginx \
  redis-server
```

安装 Node.js：

```bash
curl -fsSL https://deb.nodesource.com/setup_20.x | sudo -E bash -
sudo apt install -y nodejs
node -v
npm -v
```

## 6. 拉代码与构建

如果你直接使用当前仓库里的正式脚本，最短路径是：

```bash
sudo NewUI/yun/deployment/scripts/bootstrap_scheduler_host.sh
```

它会自动完成：

- 安装 `Redis / Scheduler / Nginx`
- 部署 `/opt/cardemo/scheduler`
- 部署 `/opt/cardemo/dashboard-web`
- 写 `/opt/cardemo/scheduler/.env`
- 启动 `redis-server / obd-scheduler / nginx`

如果你不走脚本，再按下面的手工方式执行。

```bash
sudo mkdir -p /opt/cardemo
sudo chown -R "$USER":"$USER" /opt/cardemo

git clone <你的仓库地址> /tmp/cardemo-repo
cd /tmp/cardemo-repo/NewUI/yun/scheduler

npm ci
npm run build

mkdir -p /opt/cardemo/scheduler
cp -R dist /opt/cardemo/scheduler/
cp package.json /opt/cardemo/scheduler/
cp package-lock.json /opt/cardemo/scheduler/ 2>/dev/null || true

cd /opt/cardemo/scheduler
npm ci --production
```

## 8. Redis 配置建议

当前代码直接依赖 Redis：

- `instance:{id}`
- `session:{id}`
- `device:{deviceId}`
- `instances:idle`
- `instances:all`

### 8.1 起步方案

先用本机 Redis：

```bash
sudo systemctl enable --now redis-server
sudo systemctl status redis-server
redis-cli ping
```

### 8.2 生产建议

如果后面规模继续扩大，再考虑把 Redis 独立出去。

但在你当前这个阶段，先保持：

- 1 台 Scheduler EC2
- 1 个本机 Redis

最容易把链路跑稳。

## 9. Scheduler systemd 服务

`/etc/systemd/system/obd-scheduler.service`

```ini
[Unit]
Description=OBD Scheduler
After=network.target redis-server.service
Wants=network.target redis-server.service

[Service]
Type=simple
WorkingDirectory=/opt/cardemo/scheduler
EnvironmentFile=/opt/cardemo/scheduler/.env
ExecStart=/usr/bin/node /opt/cardemo/scheduler/dist/index.js
Restart=always
RestartSec=5
StandardOutput=append:/var/log/obd-scheduler/scheduler.log
StandardError=append:/var/log/obd-scheduler/scheduler.err.log

[Install]
WantedBy=multi-user.target
```

启用：

```bash
sudo mkdir -p /var/log/obd-scheduler
sudo systemctl daemon-reload
sudo systemctl enable --now obd-scheduler
sudo systemctl status obd-scheduler
```

## 10. 调度层 Nginx 反代

## 10.1 目标

必须实现这两个外部入口：

- `http://<scheduler-host>:8080/api/...`
- `http://<scheduler-host>:8080/dashboard/...`

并把它们转发到本机 Scheduler Node。

## 10.2 Nginx 配置

`/etc/nginx/conf.d/obd-scheduler.conf`

```nginx
server {
    listen 8080;
    server_name _;

    location /api/ {
        proxy_pass http://127.0.0.1:3000/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 30s;
        proxy_send_timeout 30s;
        proxy_read_timeout 30s;
    }

    location /dashboard/ {
        proxy_pass http://127.0.0.1:3000/dashboard/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location = /health {
        proxy_pass http://127.0.0.1:3000/health;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
    }
}
```

启用：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

### 10.3 这个反代和实例层为什么能对上

因为实例层 Agent 当前会把：

`SCHEDULER_URL + /agent/health`

当成注册地址。

如果实例层 `SCHEDULER_URL` 配成：

`http://<scheduler-host>:8080/api`

那么 Agent 发出去的实际请求就是：

`http://<scheduler-host>:8080/api/agent/health`

而上面的 Nginx 规则会把：

`/api/agent/health -> /agent/health`

正好转发到 Scheduler 根路由，和当前代码完全兼容。

这就是为什么这份文档和实例层文档必须一起看。

## 11. 安全组与网络要求

## 11.1 调度层 EC2 入站

建议：

- `22/tcp`：仅运维出口 IP
- `8080/tcp`：手机 B 和实例层 Agent 都会访问

当前正式脚本在调度层机会自动尝试放行 `8080/tcp`：

- 若启用 `ufw`：自动写入 `ufw` 规则
- 若运行在 AWS EC2：自动调用 `aws ec2 authorize-security-group-ingress`

因此在 AWS 上建议给调度层实例角色授予至少以下权限：

- `ec2:AuthorizeSecurityGroupIngress`
- `ec2:DescribeSecurityGroups`

不要对公网放行：

- `3000/tcp`
- `6379/tcp`

### 11.2 调度层 EC2 出站

必须允许：

- 访问实例层 `agentPort`（默认 `4000`）
- 访问系统更新源

## 13. 调度层和实例层的耦合清单

上线前必须逐项确认：

### 13.1 与实例层一致的入口

- 实例层 `SCHEDULER_URL` 是否写成 `http://<scheduler-host>:8080/api`
- 调度层 Nginx 是否真的把 `/api/*` 转发到 Scheduler 根路径

### 13.2 控制面可达

Scheduler 会根据 Agent 上报的：

- `serverIp`
- `agentPort`

去调：

- `/instance/:id/applyCar`
- `/instance/:id/reset`

所以必须满足：

- 调度层 EC2 能访问实例层 EC2 的 `serverIp:agentPort`

### 13.3 数据面回传

调度层最终返回给手机 B 的实例地址来自：

- `publicWsHost`
- `publicWsScheme`
- `wsPort`

因此调度层文档本身不应该假设：

- 所有实例都在同一个主机端口上
- 或所有实例都走路径分流

当前代码不是这么设计的。

## 14. 调度层运行建议

### 14.1 保持地址稳定

如果你当前不准备改客户端，最稳妥的做法就是：

- 绑定 Elastic IP
- 手机 B 一直输入这个静态地址

### 14.2 不要轻易改外部端口

当前客户端硬编码入口是：

`http://<host>:8080/api`

所以不要把调度层对外改成：

- `80`
- `443`
- `3000`

除非同步改客户端。

### 14.3 当前代码还有一个运维注意点

当前调度层会记录实例 `lastHealthAt`，但不会因为 Agent 长时间不上报就自动把实例从注册表里剔除。

所以生产上建议至少加：

- `systemd Restart=always`
- Scheduler 日志监控
- Dashboard 异常巡检

---

## 15. 调度层对手机 B 的最终暴露形式

当前生产建议固定为：

- 手机 B 启动输入：`<scheduler-host>`
- 客户端实际访问：`http://<scheduler-host>:8080/api`

申请实例成功后：

- 调度层再返回实例地址
- 手机 B 后续改连：
  - `ws://<instance-public-host>:<wsPort>/ws`
  - 或 `wss://<instance-public-host>:<wsPort>/ws`

也就是说：

- 调度层只负责**入口和分配**
- 实例层负责**真正业务连接**
