# 关于实时数据流架构的分析

## 文档目的

这份文档记录对反编译得到的 CarScanner C# 源码中“实时数据流”相关架构的分析结论，重点回答两个问题：

1. 原版 CarScanner 在实时数据流页面返回主页面时，是如何做到不破坏程序进程的。
2. 这些原始设计约束，对当前 `NewUI/yun` 的 A/B 双端架构意味着什么。

这里保留细节，而不是只保留结论。后续无论是继续优化 A 端注入逻辑、B 端页面逻辑，还是让其他模型接手，都应该先理解这里面的原始运行语义。

---

## 一、原版 CarScanner 的实时数据流不是“页面线程”，而是“全局 OBD 主循环 + 页面请求源”

### 1. `OBDDataReader` 是常驻全局循环，不属于某个页面

原版实时数据流的根本前提是：真正负责和 ELM327/ECU 通信的对象是 `OBDDataReader`，它不是某个页面创建、某个页面销毁的局部对象，而是整个应用生命周期内的核心全局读写器。

关键代码：

- `OBDDataReader.ReplaceQueue(IEnumerable<OBDRequest>)` 会直接把请求集合替换成新的并发队列：
  - `CarScannerC#反编译后的源码/OBD2/OBDDataReader.cs:823`
- `OBDDataReader.Start()` 内部主循环在 `Running == true` 时持续工作；即使暂时没有请求，也不会退出，而是继续等待、必要时执行 ping：
  - `CarScannerC#反编译后的源码/OBD2/OBDDataReader.cs:1671`

这意味着：

- 页面消失，不等于 OBD 线程结束。
- 实时数据页退出，不等于蓝牙连接断开。
- 请求队列为空，也不等于进程退出。
- 真正被停止的只是“当前页面继续向 OBD 主循环提供哪些请求”。

这就是原版返回主页面后进程仍然稳定存在的第一层原因。

### 2. 原版的“实时数据页”本质上只是给请求生产器挂了一个委托

原版不是每个页面都各自维护一套独立轮询线程。它采用“请求生产器”模型：

- `RequestProducerStatic.UpdateOBDReaderRequests()` 负责收集当前所有请求生产器的输出，然后统一调用 `App.OBDReader.ReplaceQueue(...)`：
  - `CarScannerC#反编译后的源码/OBD2/RequestProducers/RequestProducerStatic.cs:10`
- `MainAppRequestProducer` 本身只是一个空壳，请求是否存在，取决于静态字段 `Delegate` 是否被当前页面设置：
  - `CarScannerC#反编译后的源码/OBD2/RequestProducers/MainAppRequestProducer.cs:10`

因此，页面与 OBD 主循环的关系是：

- 页面进入时：把“我需要哪些 PID 请求”挂到 `MainAppRequestProducer.Delegate`。
- 请求生产器刷新时：这些 PID 请求被统一送入 `OBDDataReader` 队列。
- 页面退出时：把 `Delegate` 清掉，或者让新的页面接管它。

换句话说：

- 页面不是实时流的执行者。
- 页面只是实时流的“请求配置者”和“UI 订阅者”。

## 二、原版实时页的暂停、返回、主页面恢复，是三件不同的事情

### 1. 图表页中的“暂停”只是取消订阅，不是停止 OBD 主循环

在 `LiveDataChartPage` 中：

- `Pause()` 会把 `Model0..Model3` 的订阅取消：
  - `CarScannerC#反编译后的源码/LiveDataChartPage.cs:116`
- `Play()` 会重新 `Subscribe()`：
  - `CarScannerC#反编译后的源码/LiveDataChartPage.cs:128`

这个行为的含义很重要：

- Pause 只是 UI 侧暂停更新。
- 它不是断蓝牙。
- 也不是销毁 `OBDDataReader`。
- 更不是清空整个系统状态。

所以原版“暂停”本来就很轻。

### 2. 图表页“返回”才会做完整的页面级清理

在 `LiveDataChartPage.btnBack_Clicked()` 中，原版会做这些事：

- `MainAppRequestProducer.Delegate = null`
- 对 Model 逐个 `Unsubscribe()`
- 解除 `PIDChanged` 回调
- 最后 `Navigation.PopAsync(true)`

对应位置：

- `CarScannerC#反编译后的源码/LiveDataChartPage.cs:261`

这说明原版的“返回”语义是：

1. 先让当前页面不再提供请求。
2. 再让当前页面不再订阅 PID 变化。
3. 最后才进行页面弹栈。

也就是说，原版非常明确地把“页面生命周期清理”放在导航动作之前。

### 3. 列表页的返回逻辑也遵循同样的思路

在 `LiveDataListPage.btnBack_Clicked()` 中，原版会：

- `goBackRequested = true`
- `await App.OBDReader.ClearRequestQueue()`
- 对所有 `LiveDataPIDModel` 执行 `Unsubscribe()`
- 最后 `Navigation.PopAsync()`

对应位置：

- `CarScannerC#反编译后的源码/LiveDataListPage.cs:162`

列表页消失时也会补做一遍 `Unsubscribe()`：

- `CarScannerC#反编译后的源码/LiveDataListPage.cs:246`

这说明原版并不把“页面返回”视为一个纯 UI 行为，而是一个必须伴随请求和订阅清理的完整生命周期事件。

### 4. 列表页进入时会把自己的请求重新挂回主请求生产器

`LiveDataListPage.UpdateRequests()` 会：

- `MainAppRequestProducer.Delegate = new AddRequestsDelegate(this.AddRequestsDelegate)`
- `RequestProducerStatic.UpdateOBDReaderRequests()`

对应位置：

- `CarScannerC#反编译后的源码/LiveDataListPage.cs:490`

而 `AddRequestsDelegate()` 会根据当前页面显示模式，把可见 PID 或全量 PID 转成 `OBDRequest`：

- `CarScannerC#反编译后的源码/LiveDataListPage.cs:497`

这再次说明：

- 原版实时页不是自己开线程。
- 它只是把当前页面需求转成请求，挂到全局请求生产器上。

## 三、原版返回主页面为什么不会破坏进程

### 1. 主页面不是“重建连接”，而是“重新接管请求生产器”

`SimpleMainPage.ConnectPage_Appearing()` 里最关键的几件事：

- `MainAppRequestProducer.Delegate = null`
- 若当前仍是 `ConnectedToECU`，则调用 `RequestProducerStatic.UpdateOBDReaderRequests()`

对应位置：

- `CarScannerC#反编译后的源码/SimpleMainPage.cs:482`

这里的含义是：

- 主页面出现时，会先把旧实时页留下的主请求委托清掉。
- 如果 ECU 连接仍然存在，则刷新当前主页面需要的请求集合。
- OBD 主循环没有重启，也没有被销毁。
- 只是“请求来源”从实时页切回主页面。

### 2. 因此原版的稳定性来自“请求切换”，而不是“连接重建”

原版的链路不是：

- 进入实时页 -> 新建一套后台读线程
- 返回主页面 -> 杀死线程再重建主页面线程

而是：

- 整个 App 内始终只有一个全局 OBD 主循环。
- 页面进入/退出只会改变：
  - 当前谁向请求生产器提供 PID 请求
  - 当前谁订阅 PID 值变化
  - 当前 UI 是否可见、是否更新

这是一种低耦合结构，所以不会因为页面退回就破坏进程。

## 四、原版架构对当前 A/B 双端改造的直接启示

### 1. B 端页面返回，不会天然触发 A 端原版页面生命周期

在当前项目中：

- A 端运行的是被注入后的原版 CarScanner 逻辑。
- B 端运行的是 React Native 页面。
- 两者通过 WebSocket 进行远程交互。

因此，B 端的 `navigation.goBack()`：

- 不是 A 端原版的 `Page_Disappearing`
- 不是 A 端原版的 `btnBack_Clicked`
- 不会自动清 `MainAppRequestProducer.Delegate`
- 不会自动 `Unsubscribe()` 原版页面模型

也就是说，跨端架构会天然打破“原版页面生命周期 == 运行期清理时机”的假设。

### 2. 当前项目必须显式模拟原版“停止实时流”的动作

原版本地页面靠生命周期清理；当前跨端架构只能靠远程命令把这些动作尽量模拟出来。

因此，当前项目里 `StopReadPIDs` 的职责不只是“告诉对方别读了”，而应该尽量接近原版的语义：

- 停止 JSBridge 页面层实时读取
- 清掉请求生产器委托
- 清掉 OBDDataReader 当前请求队列
- 尽可能避免残留重复请求继续回灌

这也是为什么当前 A 端 `OBDCloudManager.HandleStopReadPidsAsync()` 会出现：

- fire-and-forget 调用 `JSBridge.stopReadPIDs()`
- 清空 `MainAppRequestProducer.Delegate`
- 清空 `PIDSelectorRequestProducer.Delegate`
- `ReplaceQueue(empty)` 两次

对应位置：

- `NewUI/yun/websocket_layer/src/OBDCloudManager.cs:1565`

这是当前项目对原版本地生命周期的一种“远程模拟”。

## 五、为什么当前项目此前会在实时数据流后变得极不稳定

这一部分记录的是分析时发现的核心问题，虽然其中一部分在当前代码里已经修掉，但这些问题必须保留在文档里，因为它们解释了此前为什么会出现“开始实时流后，返回主页面、点击停止、后续操作都容易把进程带崩”的现象。

### 1. A 端曾经存在静态事件队列只入不出的内存泄漏点

此前 `WebSocketUIBridge.HandleOutgoingJS()` 中，所有从原版 JSBridge 发出的 UI 事件都会被 `Enqueue` 到静态 `OutgoingQueue`。但整个项目中没有实际消费这个队列的地方。

这个问题描述的是当时导致系统失稳的历史状态。按当前代码复核，这一问题已经被修复：实时路径不再写入该静态队列，且相关历史冗余也已从代码中删除。

问题后果：

- 每一条 `PIDValueChanged`
- 每一条状态事件
- 每一条实时 UI 回调

都会永久堆积在这个静态队列里。

实时数据流是最高频路径，所以一旦开始读 PID，这个队列就会不断膨胀。页面退回后它也不会自动清理，因为这是一个静态全局结构，不是页面局部变量。

这会导致：

- 内存持续增长
- GC 压力增大
- 后续任意操作都在更脏的系统状态上继续运行
- 表现上就是“开始实时流后，后面越来越不稳定，最后崩溃”

### 2. A 端曾经没有串行化 WebSocket 发送，实时流热点下存在并发写风险

原先的 `OBDCloudManager.SendEvent()` 在收到 `onPIDValueChanged` 时，会直接 fire-and-forget 触发 `_bridge.SendAsync(message)`。如果底层 `ClientWebSocket.SendAsync` 没有串行化，多条实时 PID 事件并发发送时就会出现危险。

实时流场景最容易击中这个问题，因为：

- `PIDValueChanged` 频率高
- 事件序列密集
- 一个页面会持续产出大量事件

如果底层发送不串行，就容易出现：

- WebSocket 写冲突
- 任务 fault
- 连接状态异常
- 未观察到的发送异常堆积
- 上层看起来像“进入实时流后后续操作也一起失控”

### 3. B 端的停止/返回语义与原版生命周期不完全一致

原版是：

- 先做清理
- 再返回页面

而当前项目中，B 端很多时候是：

- UI 先更新为“已停止”或直接返回
- `stopReadPIDs()` 后台异步发出
- 如果 A 端尚未完全停稳，用户可能立即执行下一个功能

这种“UI 先走，后台慢一点再停”的结构，在跨端场景里尤其容易导致状态错位。

### 4. B 端实时页自身也会放大热点压力

当前 RN 实时页中，收到 PID 变化时会对整个 `pidList` 执行 `map` 更新，而不是按索引精确更新单项。这不是当时最致命的问题，但它确实会放大高频数据更新对 JS 线程的压力。

## 六、对原版实时数据流架构的最终判断

### 1. 原版的稳定性来自“单一全局 OBD 主循环 + 可替换请求源”

最核心的设计点只有一句话：

- 原版 CarScanner 把“实时读取”从页面里抽走了。

页面只是：

- 配置请求
- 订阅结果
- 展示 UI

而不是承担：

- 连接生命周期
- 线程生命周期
- 主循环生命周期

所以页面退回不会损坏进程。

### 2. 原版本地架构一旦被改造成 A/B 双端，就必须手动补上跨端语义缺口

当前项目不是简单“把原版页面搬过去”，而是把原版本地页面语义拆成了：

- A 端：原版 OBD 内核
- B 端：新的 RN 实时页
- WebSocket：两者之间的桥

因此，很多原版里“页面生命周期天然成立”的假设，在当前项目里都要通过显式命令去模拟。

如果这个模拟不完整，就会出现：

- 请求没停干净
- 事件没停干净
- 连接没坏但状态机乱了
- 后续功能跑在脏状态上

## 七、对后续改造的约束建议

### 1. 任何新的实时流功能，都应该遵守原版的三个原则

1. 不新建额外的独立 OBD 主循环。
2. 尽量通过“切换请求源”而不是“反复销毁连接”来实现页面切换。
3. 页面退出时优先做订阅和请求清理，再执行导航返回。

### 2. 在 A/B 架构里，要优先维护“停止语义”的确定性

跨端实时流最怕的是：

- 页面认为自己停了
- A 端其实没停稳
- 下一个动作已经开始

所以任何与实时流相关的功能，都应该特别注意：

- stop 是否真正完成
- 队列是否真正清空
- 是否还有残留 `PIDValueChanged`
- 下一个功能是否在脏状态上启动

### 3. 原版值得保留的不是 UI 形式，而是生命周期语义

这点非常关键。

当前项目不一定需要把原版页面 UI 一比一照抄，但必须尽可能保留原版这些行为语义：

- 请求如何进入主循环
- 页面如何撤销请求源
- 页面如何取消订阅
- 主页面如何重新接管请求集合

如果这些语义保住了，实时数据流才能真正稳定。

## 八、结论

关于“原版实时数据流页面返回主页面时它是如何做的，为什么可以不破坏程序进程”，最准确的回答是：

- 原版并没有把实时数据流实现成页面私有线程。
- 它使用的是“全局 OBDDataReader 常驻主循环 + 页面级请求生产器委托 + 页面级订阅”的结构。
- 页面返回时，只是撤销当前页面提供的请求和事件订阅，再让主页面接管请求生产器。
- 连接和 OBD 主循环并没有被销毁，所以进程不会因为返回主页面而被破坏。

对当前项目而言，真正要学习的不是原版页面长什么样，而是它如何把“实时流生命周期”和“页面生命周期”解耦。
