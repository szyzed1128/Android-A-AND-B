# 当前实时数据流架构

## 文档目的

这份文档记录 `NewUI/yun` 当前实时数据流架构的实际状态，并将其与原版 CarScanner 架构做逐点对照。目标不是简单说“能跑”或“不能跑”，而是明确回答：

1. 当前架构现在是否已经满足核心稳定性要求。
2. 当前架构和原版架构相比，哪些地方已经对齐。
3. 哪些地方还存在实现差异，但目前不构成立即阻塞。
4. 后续如果继续优化，优先级应该放在哪里。

这份文档以当前代码状态为准。

---

## 一、当前架构的总体判断

### 结论分两层

#### 第一层：之前最高风险的两个问题，已经确认修复

1. `WebSocketUIBridge.HandleOutgoingJS()` 不再把 UI 事件塞进静态 `OutgoingQueue`。
   - 位置：`NewUI/yun/websocket_layer/src/WebSocketUIBridge.cs:91`
   - 这意味着此前“实时 PID 事件只入不出堆积在静态队列里”的内存泄漏点已经解除。

2. `WebSocketBridge` 已经使用 `SemaphoreSlim _sendLock` 串行化 `ClientWebSocket.SendAsync`。
   - 位置：`NewUI/yun/websocket_layer/src/WebSocketBridge.cs:26`
   - `SendAsync` 串行化位置：`NewUI/yun/websocket_layer/src/WebSocketBridge.cs:103`
   - `SendRawAsync` 也走同一把锁。
   - 这意味着此前实时流高频事件下最危险的“WebSocket 并发写”风险已经解除。

#### 第二层：当前架构已经“基本达标、可运行”，但还没有完全收口到理想状态

目前从代码结构和你的实测反馈看，当前架构已经从“高概率失稳”进入“能够稳定工作”的阶段。但它仍然和原版 CarScanner 存在若干实现差异，后续如果要进一步追求健壮性和可维护性，仍有优化空间。

## 二、当前实时数据流在 A/B 架构中的实际路径

### 1. B 端发起开始读取

当前 B 端通过 `CloudBridge.startReadPIDs(indices)` 发送请求：

- `NewUI/yun/client-app/src/services/CloudBridge.ts:325`

这和原版“页面把自己当前需要的 PID 请求挂到请求生产器”的意图是对应的，只不过当前是通过 WebSocket 把这个动作远程转发到 A 端。

### 2. A 端接收开始读取请求，并转发给 JSBridge

A 端在 `OBDCloudManager.HandleStartReadPidsAsync()` 中：

- 从消息中取出 `indices`
- 调用 `InvokeJsBridge("startReadPIDs", json)`
- 向 B 端回一个成功响应

相关位置：

- `NewUI/yun/websocket_layer/src/OBDCloudManager.cs:1517`

这说明当前架构中：

- B 端不是直接读 ECU
- A 端才是承接原版 CarScanner 内核的一侧
- B 端只是在远程请求 A 端进入实时 PID 读取模式

### 3. A 端收到 PID 变化事件后转发给 B 端

A 端收到原版回调 `onPIDValueChanged` 时，会：

- 在 `HandleUiInvokeInternal()` 中进入 `case "onPIDValueChanged"`
- 调用 `SendEvent(MessageAction.PIDValueChanged, NormalizeArg(args, 0))`

对应位置：

- `NewUI/yun/websocket_layer/src/OBDCloudManager.cs:556`

这条链是当前实时数据流的核心事件出口。

### 4. B 端收到 PID 变化后刷新页面

当前 RN 实时页会：

- 订阅 `onPIDValueChanged`
- 对 `pidList` 做映射更新
- 把匹配名称的 PID 值更新到列表中

对应位置：

- 订阅：`NewUI/yun/client-app/src/screens/LiveDataPage.tsx:72`
- 全量列表映射更新：`NewUI/yun/client-app/src/screens/LiveDataPage.tsx:109`

这部分已经能够形成功能闭环。

## 三、与原版 CarScanner 相比，当前已经对齐的部分

### 1. “A 端保留单一 OBD 内核，B 端只是页面层”的大方向是对的

原版的核心思想是：

- OBD 主循环常驻
- 页面只提供请求、订阅结果

当前项目虽然变成了 A/B 双端，但整体职责分工已经比较接近这个思想：

- A 端继续承接原版 `OBDDataReader` 内核和原版 JSBridge 行为
- B 端只负责页面层的开始/停止/展示
- 连接没有因为页面切换而被设计成必须重建

这意味着当前架构的方向是对的，不是那种“每个页面都另起一套后台读线程”的危险结构。

### 2. A 端的停止逻辑已经在尽量模拟原版“撤销请求源”语义

当前 `HandleStopReadPidsAsync()` 已经不是简单地“给 JSBridge 发一个 stop 命令”，而是做了较完整的远程清理：

- fire-and-forget 调用 `JSBridge.stopReadPIDs()`
- 清空 `MainAppRequestProducer.Delegate`
- 清空 `PIDSelectorRequestProducer.Delegate`
- 通过 `ReplaceQueue(empty)` 两次清空请求队列

位置：

- `NewUI/yun/websocket_layer/src/OBDCloudManager.cs:1565`

这与原版“页面退出时先撤销请求，再退出页面”的思路是同方向的。虽然不是本地生命周期触发，而是远程模拟，但语义已经明显比早期版本完整。

### 3. 高风险传输层问题已经修复，当前稳定性基础比之前强很多

这部分是当前架构“已基本达标”的主要依据。

#### 3.1 静态队列泄漏点已被切断

现在 `WebSocketUIBridge.HandleOutgoingJS()` 已经直接通过 `OutgoingMessage` 事件分发，不再把消息塞进那个没人消费的静态队列：

- `NewUI/yun/websocket_layer/src/WebSocketUIBridge.cs:91`

此前最危险的“开始实时流后消息无限堆积”问题已经解除。并且在当前代码状态下，`OutgoingQueue` 与 `TryDequeueOutgoing()` 这层历史残留也已经被真正删除，不再属于现存冗余。

#### 3.2 WebSocket 并发写风险已被切断

当前 `WebSocketBridge` 使用 `_sendLock` 串行化发送：

- 锁定义：`NewUI/yun/websocket_layer/src/WebSocketBridge.cs:26`
- `SendAsync` 使用锁：`NewUI/yun/websocket_layer/src/WebSocketBridge.cs:103`
- `SendRawAsync` 使用锁：`NewUI/yun/websocket_layer/src/WebSocketBridge.cs:128`

这意味着：

- 高频 `PIDValueChanged` 不会再并发压到同一个 `ClientWebSocket.SendAsync`
- 心跳和业务事件也能共享同一条串行发送通道
- 传输层稳定性相比之前显著提高

这一点非常关键，因为它直接决定实时流热点下系统是否会整体失稳。

## 四、当前架构和原版相比，仍然存在的差异

这一部分不是说当前有严重 bug，而是记录“当前能运行，但与原版仍不完全一致”的地方。

### 1. A 端 `SendEvent()` 仍然是 fire-and-forget

当前 `OBDCloudManager.SendEvent()` 中：

- 仍然是 `var task = _bridge.SendAsync(message);`
- 然后只挂了一个 `ContinueWith(...)` 做日志
- 调用点自己不等待发送完成

位置：

- `NewUI/yun/websocket_layer/src/OBDCloudManager.cs:666`

这和原版本地事件调用相比，仍然偏“异步散发”。

不过现在因为底层 `WebSocketBridge` 已经加了 `_sendLock`，这个问题已经从“高危致命问题”降级为“结构不够优雅，但可接受”。

当前判断：

- 不是立即阻塞项。
- 不是当前实测稳定性的主要威胁。
- 但如果后续需要更严格的事件顺序保障，可以继续优化。

### 2. B 端停止/返回仍然不是原版那种“先清理，再导航”

当前 `LiveDataPage.tsx` 在页面失焦时：

- 发现 `readingRef.current == true`
- 直接调用 `stopReadPIDs()`
- 立刻本地 `setReading(false)`

位置：

- `NewUI/yun/client-app/src/screens/LiveDataPage.tsx:59`

当前点击“停止读取”按钮时也是：

- 先 `setReading(false)`
- 再 fire-and-forget 调用 `stopReadPIDs()`

位置：

- `NewUI/yun/client-app/src/screens/LiveDataPage.tsx:169`

而 `CloudBridge.stopReadPIDs()` 虽然内部会等待 A 端响应，但它自身会吞掉超时异常：

- `NewUI/yun/client-app/src/services/CloudBridge.ts:338`

这和原版仍有语义差异：

- 原版更接近“先完成清理，再返回页面”
- 当前更接近“UI 先退，stop 命令后台收尾”

如果你当前实测已经稳定，这种差异暂时可以接受；但严格来说，它仍不是和原版完全等价的生命周期模型。

### 3. B 端页面更新路径仍然偏重

当前 `LiveDataPage.tsx` 对每条 PID 变化都执行：

- `setPIDList(prev => prev.map(...))`

位置：

- `NewUI/yun/client-app/src/screens/LiveDataPage.tsx:109`

这表示：

- 每次更新都要遍历整页 PID 列表
- 高频 PID 时，JS 线程压力会比较大
- 现在你没再遇到崩溃，不代表这里已经是最优结构

这不是当前最优先的问题，但它是一个明确存在的性能损耗点。

### 4. 历史冗余清理已经完成

此前为了先切断内存泄漏风险，代码一度处于“主路径不再使用 `OutgoingQueue`，但字段和辅助方法还保留”的过渡状态。

而按当前代码状态复核后，这层历史冗余已经被真正删除：

- `OutgoingQueue` 已删除
- `TryDequeueOutgoing()` 已删除

因此这一项不再属于“后续待办”，而是已经完成的清理动作。

## 五、当前架构是否已经满足要求

### 1. 如果要求是“当前版本实时流不要再一开就把系统拖崩”，答案是：基本满足

从当前代码状态和你的实测结果综合判断：

- 此前最危险的两个高风险点已经解除
- 实时流主路径不再带着明显的结构性爆点运行
- 当前已经可以认为进入“基本稳定、可持续测试”的阶段

这也是为什么当前我给出的评价是：

- “基本达标，可运行”
- 但“还没有完全收口到理想状态”

### 2. 如果要求是“与原版 CarScanner 生命周期语义完全一致”，答案是：还没有完全一致

差异主要在两个地方：

1. 当前停止/返回仍然偏 fire-and-forget，而不是严格等待停稳。
2. 当前 RN 页面更新模型仍比原版本地页面更重。

所以更准确的说法是：

- 当前已经满足核心稳定性要求。
- 当前还没有做到与原版架构完全等价。
- 但剩余差异目前更偏“优化项”，而不是“必须立刻修”的致命缺陷。

## 六、当前架构下的建议

以下建议按优先级排序。

### 建议 1：保留当前修复，不要回退

当前两项已经落地的修复是实时流稳定性的基础：

1. 不要重新引入类似 `OutgoingQueue` 的静态堆积队列
2. 保持 WebSocket 发送串行化

这两项不要回退，也不要在别处绕过它们。

### 建议 2：后续可以把 B 端 stop/back 收紧到“等待停稳再退”

当前可用，但如果继续追求与原版语义接近，建议后续把 B 端这两个点再收紧：

- 页面失焦时，优先 `await stopReadPIDs()`，再更新 UI 或退出
- 点击停止时，优先等待 A 端确认 stop 完成，再允许下一步操作

这会带来两个好处：

- 更接近原版“先清理，后返回”的生命周期语义
- 更能避免“刚 stop 就立刻执行下一个功能”带来的状态错位

### 建议 3：后续可以把 `SendEvent()` 改成统一发送泵，但不是当前阻塞项

虽然底层已经用 `_sendLock` 保住了安全性，但从结构上讲：

- `OBDCloudManager.SendEvent()` 仍是 fire-and-forget
- 如果未来事件类型更多、顺序要求更强，可以进一步升级为统一发送队列/发送泵

当前不是必须立刻做，因为最危险的并发写已经被 `_sendLock` 解决了。

### 建议 4：后续优化 B 端实时页更新粒度

当前每次 PID 更新都 `map` 整个列表。后续如果你发现：

- PID 数量增多
- 刷新频率提高
- 页面掉帧
- 低端设备卡顿

优先可以考虑：

- 改为 `index -> item` 的局部更新
- 只更新当前页可见项
- 减少对象创建和字符串格式化频率

这属于性能优化，不是当前稳定性阻塞项。

### 建议 5：保持文档与代码状态同步

`OutgoingQueue` / `TryDequeueOutgoing()` 这部分历史冗余现在已经清理完成，因此这一项不再是代码待办。

当前更重要的是：

- 后续每次再做实时流架构调整时，同步更新说明文档
- 避免文档继续把“历史问题”写成“当前仍存在的问题”
- 防止下一轮协作时被过期描述误导

---

## 七、最终结论

对“当前实时数据流架构是否满足要求”的最准确表述是：

- 是，当前已经满足核心稳定性要求，至少已经摆脱了之前那种“一旦开始实时流就把整个系统拖入不稳定状态”的高风险架构。
- 当前与原版 CarScanner 的核心思路已经对齐：A 端保留 OBD 内核，B 端更多承担页面层职责，停止逻辑也在尝试模拟原版撤销请求源的语义。
- 但当前仍然不是与原版完全等价的生命周期模型，主要差异在于：
  - A 端事件发送仍是 fire-and-forget
  - B 端 stop/back 仍没有完全做到“等待停稳再退”
  - B 端页面刷新路径仍偏重

因此，当前最合理的判断不是“已经完美”，而是：

- 当前已经进入可以继续开发和继续测试的稳定基线阶段。
- 剩余问题更多属于“收口优化项”，而不是“必须立刻修复的结构性爆点”。
